# 개인 작업기록 · 사람판단 후보 최소 검증

1. 멘토링 **전** 공유자료의 B-1·B-2·B-3·D를 복원하고 `README_B.md`, `README_D.md`, 9/23 멘토링 **후** 정리, 9/28 회의록을 대조했다. 예전 자료의 ‘IP 먼저’와 최신 자료의 ‘비IP도 비교’를 시점에 맞춰 구분했다.
2. 검증 단위를 `사용자 / 반복 업무 / 시작 사건 / 사람 결정 / 데이터 / 정답 / 8주 범위`로 통일했다. B-1은 올바른 해결 행동 이력, B-2는 실제 읽기/쓰기 영향 정의가 없어 이번 코드 실험에서 제외했다.
3. B-3와 D의 통제 사례를 `fixtures.json`에 만들고 정답 목록을 먼저 고정했다. 팀 작성 데이터이므로 현업 표본과 별개다.

## 첫 평가 → 실패 분석

- B-3 환불 기간 변경: 단어 BM25 Top 6에서 영향 자료 6개 중 3개. 영문 설정·테스트와 상담 표현을 놓치고 숫자가 같은 무관한 자료를 올렸다. 사람이 영향 목록을 바로잡은 **가상 시뮬레이션** 후 CS 문구의 `7일` 잔존을 찾아 완료를 보류했다.
- D 외부 공개: 단순 규칙이 검토 요청 6개 중 5개를 찾았다. ‘고객 단말용 라이브러리’라는 노출 표현을 놓쳤다. 이 값은 IP 판단 정확도가 아니다.

## 둘째 사례 → 다시 실패 확인

- 첫 사례의 실패를 본 뒤 `fixtures_followup.json`을 작성했다. 독립 보류셋으로 취급하지 않는다.
- B-3 무료배송 금액 변경: 영향 자료 5개 중 4개를 찾았으나, 테스트의 `50000`과 변경 지시의 `5만원`을 연결하지 못해 수정 누락 감지에 실패했다.
- D 두 번째 공개 사례: 검토 요청 4개 중 1개, 전제 변화 2개 중 0개를 찾았다. 첫 사례의 5/6만 보고 단순 규칙이 충분하다고 판단했다면 잘못된 결론이었다.

## 회고적 확장 → 해석

- B-3 검색어·영문 식별자 힌트를 넓혀 두 사례의 영향 자료 회수를 모두 채웠지만 후보 수와 무관한 자료도 늘었다.
- D 노출·기술 표현 목록을 넓혀 두 사례에서는 모든 정답을 찾았다. **두 사례를 보고 작성한 규칙**이므로 일반화 개선 근거가 아니다.
- 두 후보 모두 ‘사람이 확인할 후보를 어떻게 만들고, 이후 상태를 어떻게 검증할지’라는 구체적인 작업을 드러냈다. B-3의 완료 검증은 숫자 형식 정규화, D는 실제 IP 업무 사건/검토 기록의 정답성이 다음 병목이다.

## 다음 검증 관문

1. 다른 작성자가 만든 새로운 사례와 라벨을 **현재 규칙 수정 전에** 고정한다.
2. 실제 사람이 후보를 추가·삭제·보류하는 과정을 관찰한다. 정답표 대입 시뮬레이션을 사람 검증으로 부르지 않는다.
3. B-3은 한 정책에 연결된 여러 형식의 산출물, D는 전문가가 인정하는 검토 요청 기준을 확보한다.
4. 위 관문을 통과한 후 하나의 대시보드에 여러 후보를 얹을지 결정한다. 공통 화면 안에서도 정답·지표는 분리한다.

## 2026-09-30 · 외부 공개 사례 검증

1. 팀원 작성 사례 대신 공개 사례를 쓰기로 한 사용자 선택을 반영했다. `tobhey/finegrained-traceability`의 LibEST 자료를 Git 제외 폴더에 받았고, 원본 커밋 `197cf2f395e9e90636436f30d6383465cb9e9f63`을 고정했다.
2. 기존 BM25 검색 규칙을 수정하지 않고 요구사항 47개와 코드 파일 14개, 정답 연결 204개를 평가했다. 평균 Recall@3 0.558, Recall@6 0.760, Precision@6 0.504. 상위 6개에서 정답 일부가 빠진 요구사항은 32개다.
3. 이 공개 자료는 요구사항→코드 연결에만 정답이 있다. B-3의 영향 검색에 대한 제한된 대리 검증이며 변경 완료·한국어 동의어·D IP 판단을 증명하지 않는다. 두 팀 제작 사례에서 회고적으로 확장한 규칙의 효과도 이 결과로 입증하지 않았다.

## 검토 화면과 팀 공유 판단

1. 기존 B-3·D 사례를 하나의 정적 페이지에서 볼 수 있게 생성기를 작성했다. 정답표는 제외하고, 검토자 판단·이유를 브라우저에서 JSON으로 내려받게 했다. 사람 검토 결과는 아직 없다.
2. 팀 저장소 권한이 `WRITE`라 Git 연동형 Streamlit Cloud·Vercel·GitHub Pages는 소유자/관리자 협조가 필요하다고 확인했다. 정적 파일 공유 또는 개인 계정의 수동 Vercel 배포는 현재 준비된 화면에 맞는다. 실제 게시나 외부 공유는 진행하지 않았다.
3. 다음에는 한 명 이상이 화면을 사용해 내보낸 판단 기록을 받아 시스템 후보와 비교한다. B-3 완료 판정과 D 검토 요청은 각각 별도 독립 사례·정답이 필요하다.

## 2026-09-30 · 실제 사람 검토 기록과 회의용 MVP

1. 사용자가 전달한 첫 JSON을 해석했다. B-3에서 시스템이 놓친 상담 문구와 배송 테스트를 사람이 골랐고, D에서는 일부 누락 사건을 골랐다. release_check는 영향 범위와 실제 수정 필요성을 나눠야 하는 사례였다. ip09, ip10, q02, q08 등에 대한 사용자의 불확실성을 정답으로 고정하지 않는다. 검토 파일 자체는 개인 다운로드 폴더에 두고 저장소에 복사하지 않았다.
2. 9/30 회의는 설명 자료가 아니라 **브라우저에서 후보별로 작은 업무를 실제로 눌러보는 것**이 목적임을 확인했다. B-1·B-2·B-3·D·특허 검색 보조의 다섯 흐름을 한 정적 앱에 구현했다.
3. B-1·B-2는 합성 흐름, B-3·D는 팀 제작 기존 사례, 특허는 공개 KIPRIS 자료로 수행한 저장된 탐색 순위 일부다. 후보들의 증거 수준을 각 화면에 표시하고, 사람 선택에 따른 다음 상태를 보여준다. 서버 저장이나 새 KIPRIS API 호출은 없다.
4. 사용자 기기 로그인 후 Vercel 개인 계정의 별도 프로젝트에 정적 앱을 배포했다. 팀 저장소 Git 연결은 권한 문제로 설정하지 않았고 로컬 폴더에서 수동 배포했다. 배포 주소는 https://meeting-demo-two.vercel.app/ 이다.
5. 로그아웃 상태 HTTP 요청으로 HTML·data.js 모두 200 응답을 확인했다. 브라우저에서 B-1 승인, B-2 충돌 검사, B-3 수정 누락 보류, D 정보 부족 보류, 특허 결과 화면을 확인했다. 특허 탭은 출원번호만 제시하므로 실제 관련성 판단에는 초록·청구항이 부족하다. 회의용 흐름 시연으로만 설명한다.
