### 공개 데이터 재측정

LibEST 고정 데이터셋: 요구사항 47개·코드 파일 14개·연결 204개. 평균 Recall@6 0.760, Precision@6 0.504, 32/47개 요구사항에서 연결 일부 누락. 관련 코드 검색의 대용 실험이며 변경 완료 성능이 아니다.

특허 추가 페이지: 출원번호 정렬 첫 3개를 정답 확인 전에 고정했다. 각 검색어의 첫 500/1000/1500건을 비교했다. 인용 문헌을 후보에 넣지 않았고 출원 이전 공개 조건을 적용했다. 조회 건수는 늘었지만 이 3사례에서 인용 문헌 포함은 늘지 않았다. 일부 캐시는 첫 실패 시도에서 저장됐으므로 `new_api_calls`는 성공한 마지막 실행의 신규 요청 수이며 전체 시도 수가 아니다. 단순 페이지 확대만 우선할 근거는 부족하다. 표본이 작고 기존에 검사한 인용 양성 사례라 일반 성능 결론을 내리지 않는다.

## 검증 루프

1. 실제 HTTP·파일 실행으로 준비된 브라우저 상태와 실행 기록을 분리했다.
2. 첫 실행에서 SQLite 연결이 닫히지 않아 Windows 임시 폴더 정리가 실패했다. 연결 종료를 명시하고 전체 실행을 재시험했다.
3. KIPRIS 페이지 요청의 서버 연결 종료를 확인했다. 최대 3회 재시도와 실패 기록을 추가했고 다음 실행에서 완료했다. 실패를 성공으로 대체하지 않는다.
4. 외부 자료 결과는 출력 JSON에 실행 시각·버전·링크·한계를 함께 기록했다. 기존 평가 캐시 재측정과 새 API 조회를 구분했다.

## 재현

저장소 루트에서 순서대로 실행:

```text
python topic-validation/run_execution_poc.py
python topic-validation/evaluate_external_trace.py
python patent-evidence-poc/scripts/evaluate_candidate_generation.py
python patent-evidence-poc/scripts/probe_search_pages.py
python topic-validation/build_execution_evidence.py
```

공개 LibEST 데이터와 기존 KIPRIS 캐시는 별도 로컬 자료다. 키가 없으면 API 검증이 실패로 표시된다. API 키·원본 XML은 배포하지 않는다. `meeting-demo/execution-evidence.json`은 비밀정보가 없는 실행 결과 스냅샷이며 브라우저에서 재실행하지 않는다.

## 다음 검증 관문

- B-1: 실제/공개 이력에 실패 입력·해결 행동·성공 결과가 함께 있는지 조사. 없다면 통제 실행과 현업 수요 증거를 분리.
- B-2: 실제 자동화 도구에서 워크플로를 실행하고 읽기/쓰기 조건·병렬성·재시험 기록 확인.
- B-3: 공개 저장소의 실제 변경 전후와 테스트를 고정해 영향 탐색·누락 판정을 시험. 이번 배송 프로젝트는 통제 자료.
- D: 공개 변경 자료만으로 가능한 신호와 내부 판단 기록이 필요한 기능을 분리. IP 검토 정답은 도메인 담당자의 검토가 필요.
- 특허: 페이지 수 확대보다 검색어 표현·분류 조건을 다음 독립 변수로 시험. 후보 포함률과 후보 내 순위를 분리.

## UX 보강 순서

1. 첫 화면에서 누구의 어떤 업무인지와 첫 행동을 명확히 표시.
2. 체험 중 현재 단계·다음 행동·사람이 승인하는 대상을 가까이 배치.
3. 실제 실행 결과·저장된 조회·통제 자료·시뮬레이션을 주제마다 눈에 보이게 구분.
4. 상세 근거는 펼치기로 제공하고, 실패·보류 이유는 작업 화면에서 바로 설명.
5. 모바일·키보드 흐름과 초기화/보정 이후 결과의 일관성 재시험.

이 목록은 사전 점검 항목이며 실제 팀원 UX 피드백으로 확정한 문제가 아니다. 후속 작업에서 첫 행동·현재 안내·근거 링크·실행 수준 표시와 문제별 보정을 반영했다. 독립 AI 리뷰와 페르소나 점검 내역은 `review-loop.md`에 기록했다.
