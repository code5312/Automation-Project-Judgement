# 9/30 주제 비교용 제품 목업 검증 기록

## 목적과 증거 수준

이 결과물은 팀원이 업무를 체험하고 후보를 비교하기 위한 목업이다. 현업 수요·시간 절감·검색 정확도를 증명하지 않는다. 업무·주문·프로젝트·IP 결정은 가상이며 특허 제목과 짧은 청구항 발췌만 실제 공개 자료다. 3~5분은 체험 목표 시간이고 실제 팀원의 이해도·소요 시간은 회의에서 확인한다.

## 시나리오 선정 루프

| 후보 | 기존 설명에서 보강한 점 | 채택한 레퍼런스와 구분 |
| --- | --- | --- |
| B-1 | 상품코드가 같아도 용량·채널이 다르면 매핑을 재사용하지 않는다. 과거 해결과 재시험을 거쳐 범위를 승인한다. | [Jira 문제 관리](https://support.atlassian.com/jira-service-management-cloud/docs/what-is-the-itil-problem-management-process/)의 사건 연결·해결 이력. Jira가 이 매핑 규칙을 자동 생성한다는 의미는 아니다. |
| B-2 | 정적 충돌 경고 뒤에 실행 순서별 결과를 비교한다. 고객 관계와 CS 처리 상태를 분리해 두 정보가 보존되는지 재시험한다. | [n8n 실행 기록·재시도](https://docs.n8n.io/workflows/executions/all-executions/)와 [실행 디버깅](https://docs.n8n.io/workflows/executions/debug). 화면은 격리 실행을 모사하며 n8n을 실행하지 않는다. |
| B-3 | 업무 트리·영향 범위·변경 전후·사용자 누락 신고·재검사를 연결한다. 5만원 테스트는 보존하고 새 경계값 29,999원/30,000원 부족을 표시한다. | [Azure DevOps 추적성](https://learn.microsoft.com/en-us/azure/devops/pipelines/test/requirements-traceability?view=azure-devops)의 요구사항·코드·테스트 연결. 자연어를 임의 프로젝트에 적용하는 기능은 아니다. |
| D | SDK 공개와 서버 비공개 결정의 전제를 연결한다. 정보 부족은 개발자 답변으로 보완하고 판단 이유·전제·후속 작업을 기록한다. | [WIPO 특허 FAQ](https://www.wipo.int/en/web/patents/faq_patents)의 공개 전 검토 맥락. 법률적 결론을 규칙으로 자동 결정하지 않는다. |
| 특허 | 저장 순위·번호만 보던 화면에 실제 원문 발췌와 비교 질문을 추가했다. 문헌 추가·제외·보류 이유를 저장한다. | [WIPO 특허정보 활용](https://www.wipo.int/edocs/pubdocs/en/wipo-pub-rn2021-1e-en-wipo-guide-to-using-patent-information.pdf), 진주님 ZIP의 app.py 문헌별 decision/reason 저장. API·코드를 연결하지 않았다. |

문서와 공개 문헌의 작동 설명을 확인한 뒤 우리 시나리오에 적용했다. 레퍼런스 제품 전체를 설치·운영해 검증한 것으로 표현하지 않는다.

## 특허 원문 출처

2026/09/30 문헌 페이지의 제목과 청구항 1을 확인했다. 짧은 원문은 그대로 표기하며 한국어 설명은 요약으로 구분한다. 법적 상태·청구 범위·관련성 결론·유사도 순위는 생성하지 않는다. 준비된 문헌 순서로 표시하고 조건 필터 및 범위 확대만 모사한다. 기존 KIPRIS 평가와 별도의 자료다.

- [US9986069B2](https://patents.google.com/patent/US9986069B2/en): 통신 품질에 따른 센서 데이터 압축. 청구항 1 일부 `receive the detected link quality;`.
- [US9506776B2](https://patents.google.com/patent/US9506776B2/en): 스마트 미터 제약에 따른 샘플 선택. 청구항 1 일부 `determining a subsample of the meter sensor data;`.
- [US9268399B2](https://patents.google.com/patent/US9268399B2/en): 분류 신뢰도에 따른 추가 센서 활성화. 청구항 1 일부 `performing a first classification of the data sample from the first sensor;`.

## 동작 검증 → 보정 → 재검증

- Node 규칙 검사: 잘못된 매핑 2건 차단/조건 제한, 순서별 CRM 결과 차이/필드 분리 후 일치, 금액 동의 표현·역방향/부정 요청 차단, 상담 문구 누락, 여전히 유효한 5만원 테스트와 새 경계값 부족, 특허 2→3건 범위 확대를 검사했다.
- 브라우저 초기 실행에서 `top` 함수와 브라우저 전역 속성 충돌을 발견해 함수명을 수정하고 재실행했다.
- B-1: 넓은 규칙은 승인 차단 → 스마트스토어/350ml 제한 후 승인 → 350ml 새 주문 자동 처리 → 500ml는 사람 확인 보류.
- B-2: 두 실행 순서의 고객 상태 차이 확인 → CS 전용 필드로 수정 → 두 순서 재시험 → 두 상태 보존 및 승인.
- B-3: 요청 해석/확인 → 후보 반영 → 상담 문구·경계값 부족 검출 → 누락 신고 → 상담 반영·새 테스트 추가 → 전체 검사·완료 승인. 새로고침 후 상태 유지 확인.
- D: 판단·이유 누락 시 기록 차단 → 개발자 답변 확인 → 네 항목의 처리와 이유 저장 → 서버 유지 전제와 SDK 포함 변경 차이를 재검토 요청으로 표시.
- 특허: 실제 문헌 2건 탐색 → 판단 이유 없으면 저장 보류 → 검토 대상 저장 → 범위 확대 3건 → 다른 문헌 제외 이유 저장 → 주제 도움말 확인.
- 모바일에서 B-1 조건 입력의 가로 넘침을 발견해 선택 필드와 작업 패널의 폭을 제한했다. 나머지 후보도 모바일 폭에서 확인한다.
- 다운로드 이벤트는 브라우저 자동화에서 타임아웃됐지만 다운로드 폴더에 생성된 실제 JSON을 파싱해 스키마·입력 의견·B-3 완료·평가 기록이 포함됨을 확인했다. 인앱 브라우저와 Chrome에서 파일이 생성됐다. 다운로드가 제한된 환경을 위해 화면에서 JSON 내용을 복사할 수 있게 했다.

## 이해도 자체 점검

각 후보의 주제 선택 카드와 도움말에는 사용자·현재 문제·시스템 역할·사람 결정·체험 목표·실제 개발에 필요한 자료를 제공한다. 기본 작업 화면에는 현재 자료와 근거·다음 행동을 표시한다. 툴팁은 hover/focus/click에 반응하고 긴 설명은 모달로 연다. 자체 검토를 실제 팀원 이해도 조사로 세지 않는다.

회의 진행자는 각 체험 후 “누가 쓰나 / 기존 수고는 무엇인가 / 시스템은 무엇을 준비하나 / 사람은 무엇을 결정하나 / 다음 작업은 무엇인가”를 질문해 설명이 어려운 항목을 기록한다. 비교 점수는 주제의 실제 정확도가 아닌 팀 의견이다.

## 최종 확인과 배포

B-1 모바일 폭은 수정 후 문서 폭과 화면 폭이 모두 375px로 일치했다. 다섯 주제의 초기화와 역할 도움말을 확인했고 모달은 Escape로 닫혔다. B-3 완료 이후 사용자 편집으로 옛 문구를 되살리면 다시 완료 보류가 됐다. 직접 편집 상태와 반영된 내용이 다르지 않도록 초안을 정리하고 테스트를 편집하면 검증 완료 상태를 해제했다.

[배포본](https://meeting-demo-two.vercel.app/)에서 초기 화면·B-3 영향 반영·상담 누락·경계값 부족을 확인했다. 새 실행 오류가 없었고 배포본의 회의 JSON 실제 파일을 다시 파싱하여 검증 입력과 스키마가 일치함을 확인했다. Git 저장소와 Vercel은 자동 연동하지 않았다.
