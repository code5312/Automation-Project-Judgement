# 사람판단 주제 최소 검증

1회차 멘토링 전 공유한 B-1/B-2/B-3/D를 **같은 기준으로 비교**하고, B-3와 D를 팀 제작 통제 사례로 작게 실행한 기록이다. 최종 주제 확정이나 현업 성능 주장이 아니다. 진주님 구현 화면은 같은 팀의 별도 참고 사례이며 이 실험에 연결하지 않았다.

## 출처와 시점

- 멘토링 **전** 공유안: 저장소 `README_B.md`, `README_D.md`와 사용자가 제공한 `1회차 멘토링 프로젝트 주제 선정 방향성 논의 … .md`
- 멘토링 **후** 정리: [9/23 멘토링 이후](https://app.notion.com/p/3e934713f167810ba094d9f41c6aeb6a)
- 팀 논의: [9/28 회의록](https://app.notion.com/p/3ea34713f167816e8677ed28ccd4b147)
- 후속 가설: [사람판단 보조팀 아이디어 검증](https://app.notion.com/p/3ea34713f1678182b442f1478e45eb5b)

멘토링의 공통 요구는 `사용자·반복 업무를 좁힘 → 확보 가능한 데이터 → 기준선 → 실패 분석 → 개선 후 재평가`다. B와 D는 이 과정을 거쳐 서로 경쟁하는 후보로 남아 있다. KIPRIS 특허 검색은 D 전체가 아니라 **판단 근거 수집의 일부**다.

## 후보 카드와 첫 관문

| 후보 | 사용자·반복 업무 | 자동화 시작 → 사람 결정 → 후속 처리 | 실험 가능한 입력 | 지금 확인된 병목·첫 관문 |
| --- | --- | --- | --- | --- |
| B-1 반복 예외 자동화 | 업무 운영자·반복 예외 처리 | 예외 발생 → 규칙 후보 검토·승인 → 재발 시 실행 | 예외/해결 행동/성공 결과 기록 | **사람의 과거 해결이 올바른지** 독립적으로 확인할 실제 이력이 없음. 기록 구조와 성공 정의 확보 전까지 구현 보류 |
| B-2 자동화 충돌 사전검사 | 자동화 운영자·배포 전 검토 | 새 자동화 등록 → 충돌 수정/승인 → 배포 | n8n 정의·읽기/쓰기 계약·격리 CRM | **실제 영향 범위**를 명시한 계약 또는 실행 추적 필요. 사람판단보다 시스템 검증 성격이 강함 |
| B-3 변경 완료 검증 | PM·서비스 운영자·여러 자료의 변경 확인 | 정책 변경 → 영향 범위 확정 → 수정 업무·재검증 | 정책/FAQ/상담문구/설정/테스트 | 통제 사례 작성 가능. 표현·형식이 다른 자료 검색과 값 정규화가 병목 |
| D IP 판단 사건 탐지·재검토 | IP/R&D 담당자·공개 전 검토 누락 확인 | 외부 공개·기술 변경 → 검토 요청/판단 → 결정 전제 저장·재검토 | 개발 변경·공개 일정·가상 IP 기록 | 실제 사내 사건/결정 데이터가 없음. 합성 사례만으로 실무 수요·성능 확인 불가 |

**우선 두 실험:** B-3은 비교 가능한 자료·누락 정답을 만들기 쉽고, D는 B 원안과 구별되는 판단 순간 탐지·전제 재검토를 직접 시험할 수 있다. 이는 최종 주제 선정이 아니라 작은 검증 대상 선정이다.

## 재현

Python 3.11+와 저장소 내 BM25 코드만 사용한다. 외부 API, API 키, Streamlit이 필요하지 않다.

```powershell
cd C:\Proj\26-2-U3proj\topic_test\topic-validation
python run_validation.py
```

결과는 Git에서 제외한 `output/results.md`와 `.json`이다. `fixtures.json`에는 환불 기간 7→14일 및 외부 공개 전 IP 검토 사례를, `fixtures_followup.json`에는 무료배송 기준 5→3만원 및 두 번째 공개 사례를 담았다. 각 파일의 `gold`는 예측 함수에서 사용하지 않고 결과 계산과 **정답표를 아는 가상 검토자** 보정에만 사용한다.

## 두 번의 실행과 해석

| 사례 | B-3 영향 후보 단어 BM25 P/R | B-3 확장 후보 P/R | D 판단 요청 단순 규칙 P/R | D 확장 규칙 P/R |
| --- | ---: | ---: | ---: | ---: |
| 첫 사례 | 0.50 / 0.50 | 0.60 / 1.00 | 1.00 / 0.83 | 1.00 / 1.00 |
| 두 번째 사례 | 0.67 / 0.80 | 0.62 / 1.00 | 1.00 / 0.25 | 1.00 / 1.00 |

- **B-3:** 단어 BM25가 영문 설정·테스트와 상담 표현을 놓쳤다. 검색어/식별자 확장은 후보를 더 많이 보여줘 회수율을 높였지만, 무관한 자료도 증가했다. 두 번째 사례에서 `5만원`과 코드의 `50000`을 동일 값으로 보지 못해 수정 누락을 검출하지 못했다. 첫 사례에서는 일부러 남긴 `7일` 상담 문구를 발견해 완료 보류까지 확인했다.
- **D:** 단순 규칙은 `고객 단말용 라이브러리`, `고객용 플러그인`, `공개 API`, `새로운 ... 방법`을 놓쳤다. 표현 목록을 늘리자 이 **두 사례**에서는 모두 잡았지만, 목록을 사례를 본 뒤 만들었으므로 일반화 성능의 증거가 아니다.
- 두 번째 사례도 첫 실패를 본 뒤 저자가 만들었다. **독립 보류셋이 아니며**, 숫자를 제품 정확도나 사람 시간 절감으로 인용하면 안 된다. 사람이 후보를 어떻게 고치는지도 관찰하지 않았다.

## 회의에서 제안할 결론과 다음 검증

1. **B-3을 사람판단 팀의 대표 미니 시연 후보**로, **D 원안을 비교 후보**로 남긴다. 이유는 B-3에서 변경 → 사람 영향 확정 → 수정 → 완료 재검증의 폐쇄형 업무 흐름이 작게나마 작동했고, D는 실제 업무 자료와 전문가 판단 기준을 확보해야 설득력 있게 검증할 수 있기 때문이다.
2. 새 표현·숫자 형식·무관 자료를 포함한 **제3의 고정 사례**를 다른 팀원 또는 외부 사례에서 받아 작성하고, 현재 규칙을 바꾸지 않은 상태로 재평가한다. 이 단계 전에는 확장 규칙의 개선 효과를 주장하지 않는다.
3. 사람 검토자에게 후보 목록을 보여주고 `추가/삭제/보류` 및 이유를 기록한다. 정답표 대입 시뮬레이션과 실제 행동을 분리한다.
4. D를 계속 검토한다면 IP 담당자 또는 관련 실무자에게 **검토 누락의 실제 발생 여부·판단 카드 필수 정보**를 확인한다. 공개 KIPRIS 검색 실험은 근거 수집의 보조 결과로만 제시한다.
5. B-1은 검증 가능한 해결 이력, B-2는 자동화 계약/실행 추적을 확보할 수 있을 때 재진입한다.

## 하나의 시험 대시보드 판단

**조건부 찬성.** 별도 GitHub 저장소를 만들지 않고 이 저장소의 한 실험 공간에서 후보를 선택해 입력·후보·정답·사람 수정·실패 사례를 비교할 수 있다. 회의용 실험 환경에는 이 방식이 편하다. [Streamlit은 단일 앱의 다중 페이지와 공통 탐색을 공식 지원](https://docs.streamlit.io/develop/concepts/multipage-apps/page-and-navigation)한다.

다만 **공통 화면과 공통 저장소가 곧 공통 평가셋은 아니다.** B-3의 정답은 영향 산출물·수정 누락이고 D의 정답은 IP 검토 요청·전제 변화다. 데이터, 라벨, 지표, 실험 버전은 주제별로 분리 표시해야 한다. 화면은 현재의 `run_validation.py`와 결과 JSON을 읽는 얇은 뷰로 두고, 후보 검증이 더 진행되기 전에는 구현하지 않는다. 선택 이후에는 한 주제만 MVP로 발전시킨다.
