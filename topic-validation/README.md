1회차 멘토링 전 공유한 B-1/B-2/B-3/D를 **같은 기준으로 비교**하고, B-3와 D를 팀 제작 통제 사례로 작게 실행한 기록이다. 최종 주제 확정이나 현업 성능 주장이 아니다. 진주님 구현 화면은 같은 팀의 별도 참고 사례이며 이 실험에 연결하지 않았다.

- 멘토링 **후** 정리: [9/23 멘토링 이후](https://app.notion.com/p/3e934713f167810ba094d9f41c6aeb6a)
- 팀 논의: [9/28 회의록](https://app.notion.com/p/3ea34713f167816e8677ed28ccd4b147)
- 후속 가설: [사람판단 보조팀 아이디어 검증](https://app.notion.com/p/3ea34713f1678182b442f1478e45eb5b)

멘토링의 공통 요구는 `사용자·반복 업무를 좁힘 → 확보 가능한 데이터 → 기준선 → 실패 분석 → 개선 후 재평가`다. B와 D는 이 과정을 거쳐 서로 경쟁하는 후보로 남아 있다. KIPRIS 특허 검색은 D 전체가 아니라 **판단 근거 수집의 일부**다.

**우선 두 실험:** B-3은 비교 가능한 자료·누락 정답을 만들기 쉽고, D는 B 원안과 구별되는 판단 순간 탐지·전제 재검토를 직접 시험할 수 있다. 이는 최종 주제 선정이 아니라 작은 검증 대상 선정이다.

```powershell
cd C:\Proj\26-2-U3proj\topic_test\topic-validation
python run_validation.py
```

결과는 Git에서 제외한 `output/results.md`와 `.json`이다. `fixtures.json`에는 환불 기간 7→14일 및 외부 공개 전 IP 검토 사례를, `fixtures_followup.json`에는 무료배송 기준 5→3만원 및 두 번째 공개 사례를 담았다. 각 파일의 `gold`는 예측 함수에서 사용하지 않고 결과 계산과 **정답표를 아는 가상 검토자** 보정에만 사용한다.

## 두 번의 실행과 해석

| 사례 | B-3 영향 후보 단어 BM25 P/R | B-3 확장 후보 P/R | D 판단 요청 단순 규칙 P/R | D 확장 규칙 P/R |
| --- | ---: | ---: | ---: | ---: |
| 첫 사례 | 0.50 / 0.50 | 0.60 / 1.00 | 1.00 / 0.83 | 1.00 / 1.00 |
| 두 번째 사례 | 0.67 / 0.80 | 0.62 / 1.00 | 1.00 / 0.25 | 1.00 / 1.00 |

- **B-3:** 단어 BM25가 영문 설정·테스트와 상담 표현을 놓쳤다. 검색어/식별자 확장은 후보를 더 많이 보여줘 회수율을 높였지만, 무관한 자료도 증가했다. 두 번째 사례에서 `5만원`과 코드의 `50000`을 동일 값으로 보지 못해 수정 누락을 검출하지 못했다. 첫 사례에서는 일부러 남긴 `7일` 상담 문구를 발견해 완료 보류까지 확인했다.
- **D:** 단순 규칙은 `고객 단말용 라이브러리`, `고객용 플러그인`, `공개 API`, `새로운 ... 방법`을 놓쳤다. 표현 목록을 늘리자 이 **두 사례**에서는 모두 잡았지만, 목록을 사례를 본 뒤 만들었으므로 일반화 성능의 증거가 아니다.
- 두 번째 사례도 첫 실패를 본 뒤 저자가 만들었다. **독립 보류셋이 아니며**, 숫자를 제품 정확도나 사람 시간 절감으로 인용하면 안 된다. 사람이 후보를 어떻게 고치는지도 관찰하지 않았다.

## 회의에서 제안할 결론과 다음 검증

1. **B-3을 사람판단 팀의 대표 미니 시연 후보**로, **D 원안을 비교 후보**로 남긴다. 이유는 B-3에서 변경 → 사람 영향 확정 → 수정 → 완료 재검증의 폐쇄형 업무 흐름이 작게나마 작동했고, D는 실제 업무 자료와 전문가 판단 기준을 확보해야 설득력 있게 검증할 수 있기 때문이다.
2. 새 표현·숫자 형식·무관 자료를 포함한 **제3의 고정 사례**를 다른 팀원 또는 외부 사례에서 받아 작성하고, 현재 규칙을 바꾸지 않은 상태로 재평가한다. 공개 LibEST 자료의 요구사항→코드 검색 실험은 아래처럼 이 관문의 **일부만** 확인했다. 변경 완료와 D 판단은 아직 독립 사례가 없다.
3. 사람 검토자에게 후보 목록을 보여주고 `추가/삭제/보류` 및 이유를 기록한다. 정답표 대입 시뮬레이션과 실제 행동을 분리한다.
4. D를 계속 검토한다면 IP 담당자 또는 관련 실무자에게 **검토 누락의 실제 발생 여부·판단 카드 필수 정보**를 확인한다. 공개 KIPRIS 검색 실험은 근거 수집의 보조 결과로만 제시한다.
5. B-1은 검증 가능한 해결 이력, B-2는 자동화 계약/실행 추적을 확보할 수 있을 때 재진입한다.

## 하나의 시험 대시보드 판단

**조건부 찬성.** 별도 GitHub 저장소를 만들지 않고 이 저장소의 한 실험 공간에서 후보를 선택해 입력·후보·정답·사람 수정·실패 사례를 비교할 수 있다. 회의용 실험 환경에는 이 방식이 편하다. [Streamlit은 단일 앱의 다중 페이지와 공통 탐색을 공식 지원](https://docs.streamlit.io/develop/concepts/multipage-apps/page-and-navigation)한다.

다만 **공통 화면과 공통 저장소가 곧 공통 평가셋은 아니다.** B-3의 정답은 영향 산출물·수정 누락이고 D의 정답은 IP 검토 요청·전제 변화다. 데이터, 라벨, 지표, 실험 버전은 주제별로 분리 표시해야 한다. 선택 이후에는 한 주제만 MVP로 발전시킨다.

## 공개 자료로 검색 기준선 재확인

사용자가 외부 공개 사례를 선택해, [finegrained-traceability의 LibEST 자료](https://github.com/tobhey/finegrained-traceability/tree/197cf2f395e9e90636436f30d6383465cb9e9f63/datasets/LibEST)를 별도로 내려받아 요구사항 47개→코드 파일 14개의 공개 정답 연결 204개를 평가했다. **기존 BM25 구현과 파라미터를 변경하지 않고** 요구사항 원문을 질의, 코드 원문과 파일명을 검색 대상으로 사용했다. 정답은 순위 계산 이후에만 사용했다.

| 지표 | 결과 |
| --- | ---: |
| 요구사항별 평균 Recall@3 | 0.558 |
| 요구사항별 평균 Recall@6 | 0.760 |
| 요구사항별 평균 Precision@6 | 0.504 |
| Top 6에서 정답 연결이 하나 이상 빠진 요구사항 | 32 / 47 |

파일 개수가 14개인 작은 영문 오픈소스 프로젝트에서조차 상위 6개만 보면 연결 누락이 남았다. 이 결과는 **B-3의 영향 자료 검색에 대한 부분 대리 지표**다. 정책 변경 전후 비교·완료 판정, 한국어 동의어, D의 IP 검토 요청은 평가하지 못한다. 외부 자료와 상세 결과는 Git에서 제외한 `output/`에 두며, 공개 자료의 라이선스와 정답 출처를 유지한다.

재현하려면 저장소 루트에서 아래를 실행한다. 데이터셋은 현재 저장소에 복사해 커밋하지 않는다.

```powershell
git clone --depth 1 --filter=blob:none --sparse https://github.com/tobhey/finegrained-traceability.git topic-validation/output/external/finegrained-traceability
git -C topic-validation/output/external/finegrained-traceability sparse-checkout set datasets/LibEST
python topic-validation/evaluate_external_trace.py
```

검토자 기록용 화면은 `python topic-validation/build_review_page.py`로 `site/index.html`을 만든다. B-3와 D의 기존 두 팀 제작 가상 사례를 한 페이지에서 보고, 시스템 후보와 비교해 `영향/검토 필요·해당 없음·판단 보류` 및 이유를 남긴 뒤 JSON으로 내려받는다. **정답표는 페이지에 담지 않았다.** 실제 검토자가 기록한 결과는 아직 없으며, 페이지 사용 자체를 사람 검증으로 세지 않는다.

## 팀 공유 방식 검토

현재 저장소에 대한 접근 권한은 `WRITE`다. 팀 저장소를 연결하는 배포 설정은 소유자 또는 관리자 권한이 필요한 서비스가 있다.

| 방식 | 현재 코드와의 적합성 | 필요한 조치 |
| --- | --- | --- |
| 정적 HTML 파일 직접 공유 | 지금 만든 검토 화면을 그대로 사용 가능 | `site/index.html` 파일 공유; JSON 회수는 수동 |
| Vercel CLI 또는 Drop | 정적 화면을 팀원용 URL로 게시 가능 | 개인 Vercel 계정에서 수동 배포; 자동 Git 연결은 저장소 소유자 협조 필요 |
| GitHub Pages | 저장소의 정적 화면과 자연스럽게 연결 | 저장소 관리자에게 Pages 소스 설정 요청 |
| Streamlit Community Cloud | Python 기반 상호작용·평가 결과 통합에 유리 | 저장소 관리자 권한 또는 관리자 승인 필요; 현재 정적 화면에는 과함 |

**현재 단계의 권장안은 정적 화면을 먼저 파일 또는 수동 URL로 공유해 사람 검토 JSON을 받는 것**이다. 사용자 입력과 사례가 브라우저에서만 처리되며 서버 저장 기능은 없다. 실제 협업이 반복되고 권한이 정리된 뒤 자동 배포와 저장 기능을 선택한다. 배포 자체는 아직 하지 않았다.

## 9/30 회의용 조작 가능한 미니 MVP

사용자 목적을 다시 확인해, 설명 페이지 대신 [회의 시연 화면](meeting-demo/index.html)에 **각 후보에서 사건 → 제안 → 사람 결정 → 다음 상태**를 눌러볼 수 있는 일회성 정적 앱을 만들었다. Python 생성 스크립트 build_meeting_demo.py가 기존 B-3·D 사례와 이 채팅의 KIPRIS 탐색 기록 일부를 meeting-demo/data.js로 묶는다. 정답표·API 키·KIPRIS 원본 XML은 포함하지 않는다.

| 화면 | 직접 해볼 동작 | 데이터 성격 |
| --- | --- | --- |
| B-1 | 반복 예외 해결 규칙 승인/보류 → 다음 사건 처리 방식 확인 | 가상 사례 |
| B-2 | 새 자동화 선택 → 충돌 후보 검사 → 수정/시험 또는 검토 기록 | 가상 n8n 계약, 실제 실행 아님 |
| B-3 | 자료의 관련성·수정 상태 선택 → 완료 보류/재작업 목록 확인 | 기존 팀 제작 사례와 BM25 제안 |
| D | 사건별 검토 요청·불필요·정보 부족 선택 → 요청 목록 확인 | 기존 팀 제작 사례와 단순 규칙 제안 |
| 특허 | 저장된 KIPRIS 탐색 순위 사례 선택 → 원문 검토 대상 선택 | 실제 공개 공보 식별자·저장된 평가 순위, 새 검색 아님 |

특허 화면은 진주님 작업의 **특허 검색 후 사람 검토**와 이 채팅의 **KIPRIS 검색 평가**가 만나는 위치를 설명한다. D의 **검토를 시작해야 할 사건 탐지**와는 질문이 다르다. 번호만 제시되는 현재 화면으로 기술적 관련성을 판단할 수 없으므로 실제 제품에는 공보 초록·청구항·근거 문장이 필요하다. 회의에서 개념을 체험하는 수준으로만 사용한다.

이 정적 앱은 서버가 없고 입력을 저장하지 않는다. 회의에서 의견을 남길 때는 진행자가 따로 기록해야 한다. 또한 B-1·B-2는 코드가 작동하는 **가상 업무 시뮬레이션**이지 실제 자동화 시스템과 연동된 검증이 아니다. 배포 전에는 브라우저에서 각 탭을 한 번씩 열어 결과를 확인한다.

**회의용 배포:** [사람판단 실험실](https://meeting-demo-two.vercel.app/)을 개인 Vercel 계정의 별도 프로젝트로 게시했다. 팀 저장소 Git 연동은 설정되지 않았다. 회의 후 유지 여부는 사용자가 정할 수 있으며, 이 페이지에는 서버 저장 기능이 없어 팀원 선택 내용은 자동 수집되지 않는다.

### 9/30 주제별 작동 흐름 보강

화면 디자인에 앞서 각 업무의 최소 판정 규칙을 `meeting-demo/engine.js`로 분리했다. B-1은 수신 동의와 승인된 규칙의 적용 조건, B-2는 같은 사건에서의 쓰기 충돌·읽기 의존·중복 행동, B-3은 금액·기간의 제한적 동의 표현을 정규화한 변경 상태, D는 공개 사건과 과거 판단 전제의 재검토 신호를 계산한다. `meeting-demo/engine.test.js`로 경계 사례를 점검했다.

화면은 다섯 업무와 회의 결론을 하나의 워크스페이스에서 오가도록 개편했다. B-3·D에서는 사람의 결정과 이유를 기록하고, 마지막에 개인 JSON으로 내려받는다. 입력은 서버에 저장되지 않으므로 새로고침하면 사라진다. B-1·B-2의 입력은 가상 사례이며, B-3·D의 기존 팀 사례와 KIPRIS 탐색 결과도 실제 현장 성능의 근거로 확대 해석하지 않는다. 특히 특허 화면의 순위와 출원번호에는 초록·청구항이 없어 기술 관련성 판단을 완료할 수 없다.
