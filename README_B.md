## B. 사람 판단 중심 업무 자동화

> **“사람이 매번 같은 방식으로 확인하고 고치고 검토하는 업무를, 왜 계속 사람이 처음부터 해야 할까?”**
> 

이 방향에서는 **사람이 최종 판단은 유지하되 반복적인 판단·검토 업무를 줄이는 자동화**를 중심으로 세 가지 후보를 검토했다.

### B-1. 반복 예외 자동화

### 문제

자동화 과정에서 같은 유형의 예외가 반복 발생해도

사람이 이전과 똑같은 방식으로 다시 해결하는 경우가 있다.

예:

**예외 발생**

→ 사람이 직접 해결

→ 다음 달 같은 예외 발생

→ 다시 사람이 같은 방식으로 해결

문제는 **사람의 해결 경험이 다음 자동화에 남지 않는다는 것**이다.

### 자동화 흐름

**예외 발생**

→ **사람이 해결**

→ **해결 행동 기록**

→ **반복 패턴 발견**

→ **자동화 규칙 후보 생성**

→ **과거 사례에 재검증**

→ **사람 승인**

→ **다음 동일 예외부터 자동 처리**

### AI가 필요한 부분

- 표현이 다른 유사 예외를 같은 유형으로 묶기
- 여러 해결 행동에서 공통 패턴 찾기
- 해결법을 일반화해 규칙 후보로 설명하기

실제 자동 적용 여부는 AI가 단독으로 결정하지 않고

**성공 여부 + 정책 충돌 검사 + 과거 사례 재검증 + 사람 승인**을 통과하도록 한다.

---

### B-2. 자동화 충돌 사전검사

> **“자동화를 계속 추가하다 보면 서로 다른 자동화가 같은 데이터를 다르게 수정하지 않을까?”**
> 

### 문제

각 자동화는 개별적으로 정상 동작하지만, 여러 자동화가 같은 데이터나 시스템을 동시에 사용하면서 충돌할 수 있다.

예:

**마케팅 자동화**

고객 상태 → 관심 고객

**CS 자동화**

고객 상태 → 처리 완료

두 자동화가 동시에 실행되면 실행 순서에 따라 최종 결과가 달라질 수 있다.

### 검사할 충돌 유형

1. **쓰기-쓰기 충돌**
    - 같은 데이터를 서로 다르게 수정
2. **읽기-쓰기 충돌**
    - 한 자동화가 데이터를 읽어 판단하는 동안 다른 자동화가 값을 변경
3. **중복 실행**
    - 동일 이벤트로 결제·메일·등록 등이 두 번 수행

### 자동화 흐름

**새 자동화 등록**

→ **읽는 데이터 / 수정하는 데이터 추출**

→ **기존 자동화와 비교**

→ **충돌 후보 탐지**

→ **격리된 시험환경에서 재현**

→ **수정 또는 승인**

→ **배포**

### MVP 범위

처음부터 여러 플랫폼을 지원하지 않고,

**n8n 하나 + 가짜 CRM/DB + 충돌 3종**

정도로 제한한다.

### B-3. 변경 완료 검증

> **“정책을 바꾸라고 업무는 전달했는데, 진짜 모든 곳이 수정된 건 어떻게 확인하지?”**
> 

### 문제

예를 들어 환불 정책이

**7일 → 14일**

로 변경되면 실제로 수정해야 하는 곳은 하나가 아니다.

- 정책 문서
- FAQ
- 상담 안내문
- 자동화 규칙
- 테스트

중 하나라도 예전 값이 남아 있으면

**문서와 시스템 동작이 서로 달라질 수 있다.**

### 자동화 흐름

**정책 변경**

→ **영향받을 자료 탐색**

→ **수정 업무 생성**

→ **담당자 수정**

→ **재검증**

→ **누락 발견 시 업무 재생성**

→ **모두 반영되면 변경 완료**

### AI가 필요한 부분

- 자연어 변경 사항을 읽고 영향받을 가능성이 있는 자료 찾기
- 서로 표현이 다른 문서에서 같은 정책 개념 연결하기

최종적으로 값이 실제 변경됐는지는 가능한 경우 **규칙 기반 검증**으로 처리한다.
